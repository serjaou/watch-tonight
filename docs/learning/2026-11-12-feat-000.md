## Concepts Defended
1. **`typing.Final` vs C# `const`:**
   - In Python, type annotations (including `Final[int]`) have **zero runtime enforcement** — at runtime `MAX_PROMPT_LENGTH` is still a regular variable that could be reassigned unless a static type checker (`pyright`) blocks it.
   - In C#, `const` is baked into IL at compile time and cannot be mutated at runtime.
2. **Order of `.strip()` before `len()` & explicit rejection (Rule P4):**
   - In Python, `len("")` does *not* fail (it simply returns `0`), and `if not cleaned:` checks whether the string is empty (`""` is falsy in Python, like `string.IsNullOrEmpty(cleaned)` after `.Trim()` in C#).
   - We `.strip()` *before* checking `len(cleaned) > 500` so a 500-character prompt with accidental spaces at the end isn't falsely rejected, and we raise `PromptValidationError` instead of slicing (`cleaned[:500]`) because Product Rule P4 forbids silent truncation.
3. **`typing.TypedDict` vs Pydantic / C# `record`:**
   - `json.loads()` returns `Any` (an untyped Python `dict` at runtime). In `pyright` strict mode, indexing an untyped dict produces `Unknown` type errors.
   - `TypedDict` tells `pyright` the expected key/value types at static-analysis time, **without** validating or converting the dictionary at runtime (it remains a plain, mutable `dict`).
   - By contrast, a **Pydantic `BaseModel`** (which we will use in FastAPI and LLM outputs) validates types at runtime and can be configured as immutable (`frozen=True`), much closer to a C# `record` + `System.Text.Json` deserialization.
